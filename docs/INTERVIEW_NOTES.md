# 面试设计说明

这份说明用尽量简单的语言解释项目为什么这样设计。面试时不必背代码，重点是理解每个选择解决了什么问题。

## 1. 智能体为什么能工作

普通模型一次只返回文字。本项目把本地能力描述成一组“工具”发给模型，例如读取文件、修改文件和运行测试。模型可以返回工具名称和参数，程序执行后再把结果发回模型。

主循环只有五步：

1. 把任务、最近对话和工具说明发给模型。
2. 解析模型返回的文字或工具调用。
3. 检查路径、参数和审批结果。
4. 在本地执行工具，把结构化结果加入对话。
5. 如果模型给出最终文字就结束，否则继续下一轮。

这段循环是项目的核心，没有交给任何 Agent 框架。

## 2. 为什么使用工具调用，而不是解析普通文字

工具调用有明确的名称、JSON 参数和调用编号，比从自然语言中猜命令稳定。每个工具还提供参数规则，错误会变成统一结果，模型可以看到错误并自行改正。

## 3. 为什么工具分开实现

- `list_files`、`read_file`、`search_text` 只读取信息。
- `write_file`、`edit_file` 会修改文件。
- `run_command` 会启动本地程序。

分开后，每个工具更容易测试，也能按风险决定是否需要审批。

## 4. 如何防止无限循环

程序限制模型轮数和工具总次数。如果模型连续重复完全相同的调用，还会提前判定为卡住。命令本身也有超时。这些限制既保护电脑，也减少无意义的 API 消耗。

## 5. 如何控制上下文

模型接口不能接收无限长的历史。本项目用保守的字符预算估算大小，始终保留系统指令、原始任务和最近的完整交互。较早内容会按“模型调用工具 + 工具结果”的完整分组删除，避免只留下半段协议。单轮工具结果也有大小限制。

字符估算没有精确 tokenizer 那么充分利用窗口，但不绑定某一家模型，实现简单且可预测。

## 6. 如何保护文件和密钥

- 所有模型提供的路径都必须是相对路径，并解析到指定工作区内部。
- 符号链接不能用来绕过边界。
- `.env`、`.git`、会话目录和常见凭据文件会被拒绝。
- API Key 不会进入子进程环境；已知密钥在模型消息、工具结果和会话文件中会被替换为 `[REDACTED]`。
- 修改和命令默认都需要人工批准。

需要诚实说明：命令审批不是操作系统级沙箱。只要用户批准某条命令，它仍可能访问工作区外资源。因此危险的全自动模式只能用于可信、隔离且不含凭据的目录。

## 7. 如何处理错误

路径错误、参数错误、测试失败等工具问题不会让整个程序崩溃，而是返回给模型继续判断。网络断开、限流和服务端错误会有限重试；鉴权失败和错误请求不会重试，因为重复请求通常无用。被截断的模型回答不会被当成任务完成。

## 8. 为什么只使用 Python 标准库

题目允许模型 API 客户端库，但本项目连 HTTP 客户端也用标准库实现。这样依赖少、安装简单，并能清楚展示请求构造和响应解析。代价是目前只直接适配 OpenAI 兼容的 Chat Completions 工具调用格式，其他厂商可能需要新增适配器。

## 9. 目前的不足

- 还需要用最终选择的真实模型做稳定性验证。
- 字符预算不是精确 token 计算。
- 没有操作系统级容器或沙箱。
- 搜索工具是简单的字面量搜索，不理解语法树。
- 不会自动撤销已经批准并执行的修改。

## 10. 常见提问简答

**为什么不直接让模型输出 shell 命令？** 结构化工具更容易校验参数、区分风险、记录结果和处理错误。

**为什么编辑工具要求精确匹配？** 如果旧文本出现多次，盲目替换可能改错位置；拒绝模糊修改比猜测更安全。

**模型调用了不存在的工具怎么办？** 注册表返回 `UNKNOWN_TOOL`，模型可以根据错误重新选择。

**模型一直重复失败怎么办？** 连续相同调用会触发 `STALLED`，此外还有轮数和工具次数上限。

**为什么保留完整 Git 历史？** 题目要求评委能看到开发过程，每个阶段都有可测试的结果。

**如何证明不是假演示？** 视频先展示初始失败，再展示智能体实际查看文件、审批修改和运行测试，最后测试通过；仓库还有离线端到端测试验证完整协议链路。
